## Summary

Gardener encrypts configured etcd resources for shoot clusters using locally managed keys. It supports the `aescbc`, `aesgcm`, and `secretbox` providers, with `aescbc` as the default. Secrets are always encrypted; shoot owners can select additional resources. The key is generated by Gardener, stored as a Kubernetes Secret in the seed cluster, and injected into the kube-apiserver's `EncryptionConfiguration`. While this protects encrypted data against direct etcd access, the encryption key itself is held by Gardener.

This proposal introduces an extension point that allows shoot owners to use an external **Key Management System (KMS)** — such as AWS KMS, Google Cloud KMS, Azure Key Vault, or self-hosted solutions like [OpenBao](https://openbao.org) — to manage the etcd encryption key. The KMS plugin runs as a sidecar to the kube-apiserver in the shoot's control plane namespace on the seed. The integration follows Kubernetes' native [KMS provider v2 protocol](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/#kms-key-storage) and Gardener's existing extension architecture.

At the [Gardener Hackathon December 2024](https://gardener.cloud/community/hackathons/2024-12/#%F0%9F%94%91-bring-your-own-etcd-encryption-key-via-key-management-systems) a [prototype](https://github.com/plkokanov/gardener/tree/hackathon-kms) of this extension point was developed. This GEP is based on the Hackathon prototype and builds on the current master branch's provider API and encryption rotation flow. It reuses provider-change detection, reader and writer rollouts, resource rewriting, snapshots, and automatic completion, extending them with KMS revision tracking and extension lifecycle coordination. The prototype's KMS types and reconciliation branches are not present in master.

## Motivation

Kubernetes encryption options include identity (no encryption), local key storage (AESCBC, AESGCM, secretbox), and [KMS-based envelope encryption](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/#kms-key-storage). Gardener's established encryption flow uses local key storage. Gardener generates and stores that key, and shoot owners initiate its rotation through Gardener rather than managing it in their own KMS.

Shoot owners in regulated industries (finance, healthcare, government) are increasingly required to:

- Retain control of encryption keys ("bring your own key" / BYOK).
- Store keys in hardware security modules (HSMs) or audited KMS systems.
- Rotate keys on their own schedule via their own key management tooling.
- Prove key custody for compliance audits.

External key custody and integration with owner-operated KMS tooling require an alternative to Gardener's local key storage model. Shoot owners can already initiate local key rotation through Gardener's credential rotation operations.

### Goals

- Allow shoot owners to opt-in KMS-backed etcd encryption by enabling KMS encryption providers.
- Define a stable extension API (`ControlPlaneEncryption`) that decouples the Gardener core from any specific KMS product.
- Enable cloud providers and self-managed setups to implement KMS support by writing a Gardener extension — without changes to Gardener core beyond the extension point itself.
- Support migration from any supported local provider (`aescbc`, `aesgcm`, or `secretbox`) to KMS and back, extending the existing etcd encryption key rotation flow and its automatic completion behavior.
- Preserve decryption during rolling updates, interrupted rotations, backup restoration, and supported control plane migrations.
- Run the KMS plugin as a restartable init-container sidecar co-located with the kube-apiserver pod in the seed, matching the Kubernetes KMS v2 architecture.

### Non-Goals

- Providing a built-in Gardener integration with any specific KMS product. Concrete products (AWS KMS, Vault, OpenBao) are provider responsibility.
- Supporting KMS v1 protocol. Only the [KMS v2 API](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/#kms-key-storage) (`apiVersion: v2`) will be supported.
- Encrypting etcd for the seed cluster or the garden cluster (only shoot cluster etcd is in scope).
- Rotating the KMS key itself (i.e., rotating the key inside the KMS). That is the shoot owner's responsibility through their KMS tooling. Gardener handles the *transition* when a new key ID is presented.
- Switching directly between different extension types, such as `aws` and `openbao`, in the initial implementation. Such changes are rejected; supporting overlapping extension ownership requires a separate handover design.
- Automatic write failover between KMS providers. Multiple encryption provider entries support decryption during transitions; Kubernetes writes through the first entry.

## Background: Kubernetes etcd Encryption

Kubernetes supports encrypting Secrets and other resources stored in etcd at rest. The active provider configuration is supplied to the kube-apiserver via an `EncryptionConfiguration` file (passed via `--encryption-provider-config`). The configuration defines, per resource type, an ordered list of providers. The **first** provider in the list is used for new encryptions; all providers in the list can decrypt.

### Local Key Storage

[Local key storage](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/#local-key-storage) uses symmetric keys embedded directly in the `EncryptionConfiguration` file. Gardener currently uses the `AESCBC` provider as default:

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <base64-encoded-32-byte-key>
      - identity: {}
```

The key is generated by Gardener's secrets manager, stored as a Secret in the seed cluster, and rotated as part of the standard `etcdEncryptionKey` credential rotation flow. The shoot owner can initiate rotation but does not supply or take custody of this key. "Encrypting secret data with locally managed keys protects against an etcd compromise, but it fails to protect against a host compromise", as stated in [kubernetes.io/docs](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/#local-key-storage).

Shoot owners can select `aescbc`, `aesgcm`, or `secretbox` through `spec.kubernetes.kubeAPIServer.encryptionConfig.provider.type`. Changing that type automatically starts and completes an encryption key rotation. Manual rotation uses `gardener.cloud/operation=rotate-etcd-encryption-key`. The existing provider-specific requirements, including mandatory automatic key rotation for `aesgcm`, continue to apply; see [ETCD Encryption Config](../usage/security/etcd_encryption_config.md) and [Shoot credential rotation](../usage/shoot-operations/shoot_credentials_rotation.md#etcd-encryption-key).

### KMS Key Storage

[KMS key storage](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/#kms-key-storage) uses *envelope encryption*: the kube-apiserver encrypts resource data locally using data encryption keys (DEKs), while the KMS protects the DEK or the seed from which DEKs are derived with a key encryption key (KEK). KMS v2 caches write encryption state and decryption transformers. A plugin call is not required for every object read or write. The kube-apiserver communicates with a local plugin via a Unix gRPC socket conforming to the [KMS v2 API](https://github.com/kubernetes/kms/blob/master/apis/v2/api.proto) (`k8s.io/kms`):

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - kms:
          apiVersion: v2
          name: my-kms-provider
          endpoint: unix:///var/run/kms-provider/socket.sock
      - identity: {}
```

The gRPC server behind the socket is a **KMS plugin** — a small process that translates encrypt/decrypt requests to the KMS API. In Gardener's model, this plugin runs as a sidecar to the kube-apiserver inside the seed cluster.

Kubernetes polls the plugin's `Status()` method. A changed `keyID` causes the apiserver to update its write encryption state and recognize data protected by an older key as stale. It does **not** automatically create a `StorageVersionMigration` or rewrite all existing objects. Gardener must explicitly orchestrate rewriting and prove completion before retiring an old decryption path.

## Proposal

### User-Facing API

Shoot owners opt in to KMS encryption using `spec.kubernetes.kubeAPIServer.encryptionConfig`. Master already provides `resources` and `provider.type`. This proposal adds `kms` to the supported encryption provider types and introduces `provider.kms`, containing `type` (identifies the responsible extension) and `providerConfig` (opaque, provider-defined). Thus, `provider.type: kms` selects Kubernetes KMS encryption, while `provider.kms.type`, such as `aws` or `openbao`, selects the Gardener extension. External encryption always uses KMS v2.

```yaml
apiVersion: core.gardener.cloud/v1beta1
kind: Shoot
spec:
  kubernetes:
    kubeAPIServer:
      encryptionConfig:
        # optional resources in addition to Secrets, which are always encrypted
        resources:
          - configmaps
        # select KMS encryption and its provider extension
        provider:
          type: kms             # aescbc (default) | aesgcm | secretbox | kms
          kms:                  # required if and only if type is kms
            type: aws           # extension type, registered for kind ControlPlaneEncryption
            providerConfig:     # opaque to Gardener, validated by the extension
              apiVersion: aws.provider.extensions.gardener.cloud/v1alpha1
              kind: ControlPlaneEncryptionConfig
              keyARN: "arn:aws:kms:eu-central-1:111122223333:key/1234abcd-12ab-34cd-56ef-1234567890ab"
              region: eu-central-1
```

The `provider.kms.providerConfig` is opaque to Gardener core — its schema is defined entirely by the provider extension (here, a hypothetical AWS provider). An OpenBao provider would use a different shape; see [Example: OpenBao as a KMS Provider](#example-openbao-as-a-kms-provider).

The existing default for an omitted `provider.type` remains `aescbc`. Shoots using local encryption, including those with only `resources` configured, retain their behavior. The following validation rules apply:

- `provider.kms` is required if and only if `provider.type` is `kms`. Its `type` must be non-empty and its `providerConfig` must be non-null. Partial configuration is rejected.
- The extension must register support for kind `ControlPlaneEncryption` and the requested `provider.kms.type` through `ControllerRegistration`.
- `resources` continues to contain only additional resource types; explicitly listing `secrets` is rejected by existing validation.
- Direct changes between two KMS extension types in `provider.kms.type`, such as `aws` and `openbao`, are rejected initially. Changes to `provider.type` between local providers and `kms` are supported migrations.
- Existing validation for rotation readiness, unfinished encryption changes, hibernation, and simultaneous provider/resource changes is reused and extended to `provider.kms` changes. Provider or KMS configuration changes and resource-coverage changes cannot be combined in one update or overlap an unfinished encryption transition.
- To migrate back to local encryption, set `provider.type` to `aescbc`, `aesgcm`, or `secretbox` and remove `provider.kms` in the same update, preserving `resources`. Omitting the provider configuration selects the existing AESCBC default. Removing only `provider.kms` while leaving `provider.type: kms` is invalid.
- Removing the entire `encryptionConfig` also removes additional resource coverage. If this would change both provider and resource coverage, first migrate to a local provider, then remove resource coverage in a separate update.
- Existing local-provider constraints still apply when selecting a local target, including automatic encryption-key rotation and its maximum rotation period for `aesgcm`.

Provider extensions validate their own configuration and retain the last usable configuration if validation or provisioning fails. Credentials and key material must not be embedded in `providerConfig`; providers define references to authorized credentials instead.

The provider is tracked in the existing `status.credentials.encryptionAtRest.provider.type`, extended to accept `kms`. Rotation progress remains in `status.credentials.rotation.etcdEncryptionKey`. This proposal adds optional KMS information under `status.credentials.encryptionAtRest.provider.kms`:

| Field | Meaning |
|---|---|
| `type` | Extension type used by the completed KMS configuration. |
| `revision` | Opaque configuration and write-key revision established at creation or by the last completed transition. |

Gardenlet records these fields after initial activation and updates them when a transition completes. During a transition, the existing provider status continues to describe the last completed configuration, while rotation status identifies the captured target. On completion of migration to a local provider, gardenlet updates `provider.type` and removes `provider.kms`. The completed KMS revision allows a later external-key change to be detected even though `provider.type` remains `kms`. Historical recovery information is retained separately as described below.

### Extension Resource: ControlPlaneEncryption

A new extension resource `ControlPlaneEncryption` is introduced in the `extensions.gardener.cloud` group. The gardenlet creates one `ControlPlaneEncryption` object per shoot using KMS in the shoot's control-plane namespace on the seed. It maps the Shoot's `encryptionConfig.provider.kms.type` and `providerConfig` to the extension resource's `spec.type` and `spec.providerConfig`. The provider extension's controller reconciles it and writes the resulting KMS configuration into the status.

The following CRD excerpt illustrates provider configuration validation. Common extension fields and the rotation coordination fields described below must be included in the generated schema; this excerpt is not a complete CRD to install.

```yaml
apiVersion: apiextensions.k8s.io/v1

  name: controlplaneencryptions.extensions.gardener.cloud
```

**Rotation coordination:**

The prototype's two status lists do not express a safe handover by themselves. This proposal adds the following fields; they are not yet implemented by the prototype:

| Field | Writer | Meaning |
|---|---|---|
| `spec.rotation.id` | Gardenlet | Unique identifier for the transition. |
| `spec.rotation.targetRevision` | Gardenlet | Desired revision captured at the start of the transition. |
| `spec.rotation.stage` | Gardenlet | `PrepareReaders`, `ActivateWriter`, or `RetireReaders`. |
| `status.desiredRevision` | Extension | Opaque, stable revision identifying the desired backend configuration and write key identity, including an addressable version where applicable. |
| `status.observedRotation` | Extension | Acknowledged transition ID, target revision, and stage after the corresponding work succeeds. |
| `status.writeKeyID` | Extension | KMS v2 key ID expected from the plugin for the acknowledged write configuration. |
| `status.targetProviderName` | Extension | Name of the KMS configuration serving the captured target revision; absent for a local target. |

Gardenlet also persists `rotationID` and `targetRevision` in `status.credentials.rotation.etcdEncryptionKey` so retries and restores resume the same transition. The CRD must validate the stage enum and require all rotation fields together. Local targets use a Gardener-owned revision identifying the persisted local key; the extension treats that revision as a handover to local encryption rather than a KMS key ID.

`status.apiServerKmsEncryptionConfigs` and `status.activeProviderEncryptionConfigs` describe all plugin instances needed by the acknowledged stage. Their entries correspond by index, must have equal lengths, and must use unique provider names and socket paths. Gardenlet validates this contract before using the status. It uses `targetProviderName` and the acknowledged stage to construct encryption order rather than assuming the first status entry is always the write provider. Provider-specific mappings remain opaque to core in `status.state`. Historical configuration snapshots remain available until their retirement is authorized. For local targets, `writeKeyID` describes the retained KMS writer during reader preparation and is absent once local writes are activated; gardenlet verifies the local key identity instead.

Provider names form part of the stored ciphertext prefix and must remain stable for data they need to decrypt. A provider name is distinct from the KMS `keyID`, which identifies the external KEK, including its version where exposed by the backend. Refreshing credentials alone should not unnecessarily change either identity.

**Object lifecycle:**

| Event | Action |
|---|---|
| Shoot created with `provider.type: kms` and a valid `provider.kms` | Create CPE, persist recoverable state, acknowledge the initial write configuration, then deploy kube-apiserver. |
| Shoot reconciled without a change | Reconcile CPE and validate status against the current generation and rotation request. |
| KMS configuration or external write key changes | Capture a target revision and execute staged rotation while retaining old decryption. |
| Local provider selected and `provider.kms` removed | Keep CPE and its webhook active throughout migration to the selected local provider; delete CPE only after all apiservers have stopped using KMS. |
| Shoot deleted | Retain KMS access until operations requiring the Shoot API finish and kube-apiserver is stopped; then delete CPE. |

### Extension Controller Contract

Provider extensions implement the following lifecycle operations. The signatures illustrate the required responsibilities; the prototype currently implements only reconciliation and deletion.

```go
type Actuator interface {
    // Reconcile discovers desired keys, preserves historical configurations,
    // and prepares plugin settings for the requested rotation stage.
    Reconcile(ctx context.Context, log logr.Logger,
        enc *extensionsv1alpha1.ControlPlaneEncryption,
        cluster *extensionscontroller.Cluster) error

    // Delete releases plugin resources after gardenlet has stopped using them.
    // It does not destroy customer keys or keys needed by retained backups.
    Delete(ctx context.Context, log logr.Logger,
        enc *extensionsv1alpha1.ControlPlaneEncryption,
        cluster *extensionscontroller.Cluster) error

    // ForceDelete releases extension resources during forced Shoot teardown.
    // It does not authorize destruction of external key material.
    ForceDelete(ctx context.Context, log logr.Logger,
        enc *extensionsv1alpha1.ControlPlaneEncryption,
        cluster *extensionscontroller.Cluster) error

    // Migrate freezes state for transfer without revoking source decryption.
    Migrate(ctx context.Context, log logr.Logger,
        enc *extensionsv1alpha1.ControlPlaneEncryption,
        cluster *extensionscontroller.Cluster) error

    // Restore reconstructs historical and active plugin configurations before
    // the target kube-apiserver starts.
    Restore(ctx context.Context, log logr.Logger,
        enc *extensionsv1alpha1.ControlPlaneEncryption,
        cluster *extensionscontroller.Cluster) error
}
```

The `Reconcile` implementation must:

1. Validate `providerConfig` and resolve authorized credential references.
2. Verify key access, including an encrypt/decrypt round trip, and discover the desired write key identity. Controller verification does not replace verification from the plugin's own identity and network path.
3. Retain the current configuration and publish `desiredRevision` without prematurely switching plugin writes to it.
4. Prepare all endpoints, historical configuration snapshots, and recovery metadata required by the requested stage. Never overwrite the only copy of an old decryption configuration.
5. Publish matching KMS configurations and active provider configuration snapshots, then acknowledge the exact rotation request in status.

The extension periodically checks the backend for key changes even when the Shoot specification is unchanged. A change to `desiredRevision` must enqueue gardenlet reconciliation. Providers must support selecting the target KMS key identity so gardenlet can coordinate activation; versions must be pinned when they form part of that identity. Backends that cannot preserve historical decryption and coordinate changes of write key identity are unsupported initially.

A backend may rotate internal key material transparently behind a stable KMS key identity while preserving decryption. Such rotation does not necessarily change `keyID` or require a Gardener rewrite. Each provider must document this distinction; a version-addressable Transit key and a cloud KMS key with transparent internal rotation need not expose identical rotation semantics.

The extension framework supplies finalizers, operation annotations, and status updates. A successful operation must acknowledge the current generation and requested stage. The namespace label `gardener.cloud/control-plane-encryption-provider: <type>` selects the extension's Deployment webhook. Gardenlet retains this label from the active CPE while migrating back to local encryption, even after the Shoot's KMS fields have been removed.

CPE readiness before deployment means configuration and recovery state are prepared; it does not mean a not-yet-created plugin socket is serving. A finalizer alone does not protect the endpoint: gardenlet must not request CPE deletion until running apiservers no longer require it.

### Extension Webhook Contract

After the `ControlPlaneEncryption` CR becomes `Ready`, the gardenlet deploys the kube-apiserver. Before the Deployment is applied, a **mutating webhook** registered by the provider extension injects the KMS plugin sidecar:

```go
type Ensurer interface {
    // EnsureKubeApiserverDeployment mutates the kube-apiserver Deployment to inject
    // the KMS plugin as a restartable init container alongside the required volume and
    // volume mount for the Unix socket.
    EnsureKubeApiserverDeployment(
        ctx context.Context,
        controlPlaneEncryption *extensionsv1alpha1.ControlPlaneEncryption,
        deployment *appsv1.Deployment,
    ) error
}
```

The webhook must select the kube-apiserver Deployment in namespaces labelled with its provider type, find the container by name (`kube-apiserver`), and reconcile injection idempotently. It injects every plugin needed by the acknowledged stage and removes obsolete containers, mounts, and volumes only after retirement is authorized. Missing or inconsistent CPE status must reject mutation. Admission configuration must fail closed when a required webhook cannot be reached.

**Sidecar injection pattern**

```yaml
# injected by the provider webhook into the kube-apiserver Deployment:
initContainers:
  - name: kms-plugin-<provider>
    image: <provider>/kms-plugin:<version>
    restartPolicy: Always          # restartable init container (Kubernetes 1.29+)
    args:
      - --listen=/var/run/kms-plugin/socket.sock
      - --key-name=...  # provider-specific
    startupProbe:
      exec:
        command: ["/kms-healthcheck", "--socket=/var/run/kms-plugin/socket.sock"]
      periodSeconds: 5
      failureThreshold: 60
    readinessProbe:
      exec:
        command: ["/kms-healthcheck", "--socket=/var/run/kms-plugin/socket.sock"]
      periodSeconds: 10
    volumeMounts:
      - name: kms-plugin-socket
        mountPath: /var/run/kms-plugin
volumes:
  - name: kms-plugin-socket
    emptyDir: {}
# added to the kube-apiserver container:
# volumeMounts:
#   - name: kms-plugin-socket
#     mountPath: /var/run/kms-plugin
```

Using a **restartable init container** (`restartPolicy: Always`) starts the sidecar before application containers and restarts it after a crash. Process startup alone does not prove cryptographic readiness: the startup probe must verify socket availability and usable cryptographic service before kube-apiserver starts. The illustrated health command is schematic and must be supplied by the provider image. Readiness reflects ability to serve the required configuration; liveness should detect a stuck process without restarting all plugins merely because the backend is unavailable.

Native sidecar support is a requirement on the **Seed** Kubernetes version and feature configuration, since the Seed runs these pods. The extension defines socket permissions, resource requests and limits, restricted security contexts, and separate credential and CA mounts. Tokens must not be passed as literal command-line arguments.

### Gardenlet Integration

KMS integration extends the existing encryption key rotation flow. The following building blocks are already available in master:

| Existing implementation | Reuse for KMS |
|---|---|
| Provider comparison and `startRotationETCDEncryptionKey` in the [Shoot reconciler](../../pkg/gardenlet/controller/shoot/shoot/reconciler.go) | Start the existing `Preparing` phase when `provider.type` changes, with automatic completion enabled. Add revision-based triggers for changes that keep `provider.type: kms`. |
| `computeAPIServerETCDEncryptionConfig` and `handleETCDEncryptionKeyRotation` in [shared API-server handling](../../pkg/component/shared/apiserver.go) | Populate the new decryption path while writing through the old one, wait for rollout, then activate the new writer. Extend the rollout barriers with CPE acknowledgement and KMS write-identity verification. |
| `ReconcileSecretETCDEncryptionConfiguration` and `generateEncryptionProviders` in the [encryption configuration builder](../../pkg/component/apiserver/encryptionconfiguration.go) | Preserve provider ordering and support mixed local/KMS entries. Master currently constructs only local providers from current and old key Secrets; KMS configuration generation must be added. |
| Rewrite, snapshot, and finalization tasks in the [Shoot reconciliation flow](../../pkg/gardenlet/controller/shoot/shoot/reconciler_reconcile.go) and [encryption rotation utilities](../../pkg/utils/gardener/secretsrotation/etcd.go) | Retain task ordering, retries, backup conditions, and cleanup; make progress tracking independent of local key Secrets. |
| `ValidateEncryptionConfigUpdate` in [Shoot validation](../../pkg/api/core/validation/shoot.go) | Extend existing serialization and readiness checks to KMS configuration changes and pending external-key transitions. |

The extended reconcile flow includes the following barriers:

1. Create or reconcile CPE; retain the previous usable configuration if preparation fails.
2. Capture a transition ID and target revision when needed; persist recovery state before enabling writes with new key material.
3. Request and await the extension's acknowledgement for the current stage and generation.
4. Build `EncryptionConfiguration`, apply the Deployment, and wait for all serving kube-apiserver replicas to use the expected configuration. Verify plugin key IDs and the apiservers' observed write identities from the actual pods; plugin `Status()` alone does not prove each apiserver has refreshed its cached write state.
5. Explicitly rewrite affected resources after the write-activation barrier, then take a full etcd snapshot where backups are configured before marking the transition `Prepared`.
6. Automatically advance to `Completing`, remove retired decryption paths, await rollout, and clean up plugin resources. On migration to a local provider, delete CPE only after this rollout. Update provider status and mark the transition `Completed` after successful finalization.

Local providers continue to use the secrets manager for key generation, retention, and persistence. KMS entries come from acknowledged CPE status and contain endpoint and provider identity information rather than a locally generated symmetric key. The configuration builder must support local-to-KMS, KMS-to-local, and KMS-to-KMS revision transitions, including multiple KMS entries when needed.

`RewriteEncryptedData` already selects between creating and monitoring `StorageVersionMigration` objects and rewriting resources through metadata patches. KMS reuses both paths and the existing version/feature selection. In the current implementation, [StorageVersionMigrator selection](../../pkg/utils/gardener/shoot.go) enables the migration path for Shoot Kubernetes versions >= 1.37 when the required features and API are enabled; older versions use metadata patches. A plugin `keyID` change does not itself create a migration: gardenlet must still invoke the rewrite flow after the writer barrier.

Both rewrite paths currently look up the current `etcd-encryption-key` Secret and use its name as a rotation label. Reader preparation, rewrite completion, and snapshot completion also use boolean Deployment annotations. For transitions involving KMS, generalize these helpers to accept a durable transition identity without requiring a local key Secret. Scope labels, migration objects, and completion markers to the captured `rotationID` and `targetRevision`, using valid derived names or labels where needed. Retries may reuse progress only for that same transition; a marker or successful migration from an earlier revision must not skip new work. Existing local-only rotation behavior remains supported.

The current API-server wait checks Deployment rollout. For KMS, that check is extended with the plugin and API-server identity checks described above. A healthy rollout alone does not prove that every apiserver has selected the expected external write key. CPE stages coordinate the extension with the existing rotation phases; they do not replace the Shoot rotation state machine.

Changing resource coverage also reuses the existing rewrite flow. When a resource is removed, its configuration temporarily writes through `identity` while retaining the previous decryption provider until rewriting and snapshotting complete. For KMS, the rewrite records the active KMS revision and the requested coverage change in its transition identity. Secrets always remain encrypted. Resource-coverage changes and key/provider transitions are serialized, including backend revisions discovered while coverage is changing.

### Key Rotation and Provider Migration

#### Trigger and ownership

Gardenlet owns the transition and durable progress; the extension owns backend discovery and plugin configuration. Changing `encryptionConfig.provider.type` between a local provider and `kms` uses the existing provider-change trigger. Updating `provider.kms.providerConfig` or discovering a different external write key may leave `provider.type` unchanged; gardenlet compares the extension's `status.desiredRevision` with the completed revision in Shoot provider status and starts the same rotation flow when they differ. Credential refreshes can be applied without rewriting data if the provider confirms that key identity and decryption behavior are unchanged.

Once preparation succeeds, all provider changes and externally discovered revision changes complete automatically through `Preparing` → `Prepared` → `Completing` → `Completed`, matching master's provider-change behavior. The extension must not activate a pending revision outside this flow. A spec update alone is not proof of a usable target: gardenlet must obtain the acknowledged revision and persist recovery state before activating writes.

The existing `gardener.cloud/operation=rotate-etcd-encryption-key` operation while using KMS requests discovery and a rewrite under the selected external key, followed by automatic completion. A fresh rotation ID is allocated even if the selected KMS revision is unchanged, so a previous completion marker cannot suppress the requested work. The operation does not rotate the external KEK itself. Scheduled automatic encryption-key rotation and combined credential-rotation operations use the same KMS transition machinery and do not acquire ownership of external key rotation.

KMS uses the single-operation rotation interface. Master already rejects `rotate-etcd-encryption-key-start` and `rotate-etcd-encryption-key-complete` for Shoots running Kubernetes >= 1.34. Existing legacy behavior for older local-encryption Shoots is preserved, but KMS does not introduce a separate manual-completion requirement. Combined credential operations retain master's version-dependent behavior for other credentials; their KMS rotation completes automatically.

Automatic completion authorizes removing obsolete readers from the live apiserver configuration after all barriers pass. It does not authorize destroying external keys or discarding recovery metadata required by retained backups.

#### Stages and HA invariants

The same state machine applies to local-to-KMS, KMS-to-local, and supported KMS configuration/key changes:

Snapshot barriers apply whenever etcd backups are configured, matching Gardener's existing backup behavior. Without etcd backups, gardenlet records that snapshotting is not applicable and still requires successful rewriting and durable key metadata; recovery of a lost etcd dataset is not promised. A configured backup failure must never be treated as this exception.

| Shoot phase | CPE stage | Required action and completion barrier |
|---|---|---|
| `Preparing` | `PrepareReaders` | Persist recovery metadata. Deploy all required old and new decryption paths while continuing to write through the old provider. Every serving apiserver must be able to read the target format. |
| `Preparing` | `ActivateWriter` | Switch writes to the target while keeping old decryption. Wait until every serving apiserver uses the target configuration and expected key ID, and old writers have stopped. |
| `Preparing` | `ActivateWriter` | Rewrite all configured encrypted resources under the target; retry failures without discarding old decryption. Take a full etcd snapshot after successful rewriting. |
| `Prepared` | `ActivateWriter` | Record successful rewrite and the required snapshot for this transition. Automatically enter `Completing`; keep old decryption until the retirement rollout. |
| `Completing` | `RetireReaders` | Remove obsolete decryption entries and sidecars, await rollout, then release unused plugin resources. Preserve recovery information needed by retained backups. |
| `Completed` | `RetireReaders` | Record the completed provider in `status.credentials.encryptionAtRest.provider.type` and its KMS extension type/revision in `provider.kms` when applicable. Finalize progress markers; retained backup dependencies remain protected. |

For initial Shoot creation there is no old encrypted dataset: gardenlet persists initial recovery state and activates the initial configuration before starting the first apiserver.

A plugin supporting multiple key versions may serve both readers through one endpoint. A change to provider configuration or ciphertext prefix may instead require two plugin instances and two provider entries. Either implementation must preserve decryption across all serving replicas. The extension pins write versions until the requested activation stage; a backend's default latest version must not bypass the rollout barriers.

Gardenlet persists each barrier and resumes the same transition after a restart. Failure to verify every serving replica, a partial rewrite, or a failed snapshot leaves the transition incomplete and retains old keys. If the observed write key changes unexpectedly, gardenlet must not mark rewriting complete: it reports the mismatch and re-establishes a consistent target before repeating the rewrite. Rollback after target writes have begun must retain target decryption and perform a reverse transition, rather than simply reverting configuration.

User changes to the target configuration are rejected while a transition is unfinished. Backend changes discovered during a transition are recorded as pending work; the captured target remains pinned. Further transitions start only after the current one completes. Key owners must keep all referenced versions enabled throughout this process.

#### Migrating from a local provider to KMS

The following example uses the default AESCBC provider. The same ordering applies with AESGCM or secretbox as the local provider.

| Stage | EncryptionConfiguration provider order |
|---|---|
| Prepare all readers | `AESCBC` (old key), `KMS` (target), `identity` |
| Activate target writer after reader rollout | `KMS` (target), `AESCBC` (old key), `identity` |
| Rewrite and snapshot after writer rollout | Same order; all configured encrypted resources are rewritten. |
| Retire old reader during automatic completion | `KMS` (target), `identity` |

`identity` permits reading existing plaintext during coverage changes; it is not an encryption fallback on KMS failure.

#### Migrating from KMS back to a local provider

The reverse path uses the selected local provider (`aescbc`, `aesgcm`, or `secretbox`), with AESCBC as the default. For an AESCBC target, it first generates and persists the local key, then rolls out `KMS, AESCBC, identity` so all readers know the local key. It next rolls out `AESCBC, KMS, identity`, waits for all writers, rewrites, and snapshots where backups are configured. Only during automatic completion does it remove KMS from the configuration and Deployment. After every apiserver uses `AESCBC, identity`, gardenlet deletes CPE and removes its namespace selector label. AESGCM and secretbox targets follow the same sequence with the selected local provider.

The extension's `Delete` operation must never run before this handover completes. A user must migrate back to local encryption before choosing another extension type in a subsequent transition; direct cross-extension migration is initially rejected.

### Backup, Recovery, and Control Plane Migration

KMS-backed etcd backups require both the external keys and sufficient metadata to reconstruct the decryption configuration. A backup of ciphertext alone is insufficient.

The extension stores generated recovery metadata in CPE `status.state` and references necessary Kubernetes resources through the standard extension status resource mechanism. This includes active and historical provider names, backend identity, concrete key versions, configuration revisions, and credential references. Plaintext KEKs and access tokens must not be copied into status. Any future provider using an encrypted local wrapping key must persist every required encrypted key and its lookup mapping as part of this state.

Writing `status.state` on the Seed is not itself a recovery guarantee. Master's existing persistence of local key Secrets does not supply KMS recovery state. Implementation must integrate the new `ControlPlaneEncryption` resource into ShootState collection, persistence, restoration, and lifecycle handling. Gardenlet must synchronously persist recoverable state in the garden before enabling writes with a newly introduced key or configuration. Periodic ShootState backup alone leaves a data-loss window. Recovery metadata must remain available while a transition is pending or CPE is being retired.

After rewriting, a new full etcd snapshot provides a recovery point for the new state when backups are configured. Retained older full and delta snapshots may still depend on older provider configurations and key versions. Removing an old reader from a running apiserver is distinct from deleting its external key or recovery metadata. The extension and gardenlet must retain the necessary state in ShootState outside the CPE lifecycle, including when CPE is deleted after migration to a local provider. ShootState collection must preserve these archived entries instead of dropping them because the source CPE no longer exists. Key retirement is permitted only when no supported recovery point needs that key; the retention policy must be explicit and aligned with backup retention. Customer key destruction is never an implicit consequence of automatic rotation completion, `Delete`, or `ForceDelete`.

If Shoot deletion retains backups beyond the lifetime of ShootState, its recovery archive must be preserved with those retained backups before ShootState is deleted. Credential references must resolve to renewable access on restore; persisting a reference to an expired or deleted Seed-only token is insufficient.

Control plane migration follows this order:

1. Reject migration during an unfinished encryption transition. Verify the destination supports the extension, Seed-side sidecars, backend network access, and credential bootstrap for all required key versions.
2. Freeze configuration changes and preserve source decryption until source operations needing the Shoot API finish. Invoke `Migrate` and durably capture final extension state through ShootState before source cleanup.
3. Restore state, credential references, and plugin configuration on the destination. Invoke `Restore` and verify access using the destination identity before starting kube-apiserver against restored etcd data.
4. Start and verify destination apiservers. Retire source plugin resources according to the existing control plane migration lifecycle without revoking shared external keys.

Unplanned Seed loss uses previously persisted state and retained keys without requiring the source to run `Migrate`. Restoration of an older backup must select matching historical decryption configurations even if the current Shoot spec no longer names them. Bootstrap must not require an already functioning Shoot API.

Until these paths are implemented and verified, KMS-enabled control plane migration must be rejected explicitly. Production enablement requires recovery from Seed loss; it cannot rely on the source Seed remaining available.

### Security and Availability

External KMS custody protects the external KEK from being stored as a Gardener-managed plaintext key. It does not prevent a compromised Seed host, apiserver, or sufficiently privileged Seed operator from obtaining resource plaintext or using an authorized plugin. The threat model must distinguish stored-backup compromise from compromise of a running control plane.

Each provider must define:

- Per-Shoot credentials and authorization limited to the intended key paths and operations, including historical decryption. Shoot-supplied configuration must not grant arbitrary access to unrelated Seed Secrets or keys.
- TLS certificate validation and CA distribution, network policies, and backend reachability from both the controller and every plugin pod.
- Credential bootstrap, expiry, renewal, and recovery without depending on the encrypted Shoot API. Use mounted credentials or projected service account tokens; never embed tokens in command-line arguments, status, or logs.
- Idempotent plugin restarts, bounded request timeouts, and metrics for backend errors, plugin readiness, expected key-ID mismatches, and stalled rotation stages.
- Behavior during KMS outages. Cached operations may continue for a time, depending on Kubernetes encryption state and plugin behavior; cold starts and decryption cache misses can require the backend. Do not promise indefinite availability from caching.

A KMS error must never cause silent plaintext writes or fallback to local encryption. Existing healthy apiservers should remain available while a replacement pod cannot initialize its plugin. Rollout policy and probes must be tested under backend failure so an update does not unnecessarily remove all healthy replicas. Hibernation wake-up requires the same independent credential bootstrap and key access as a cold restore.

## Example: OpenBao as a KMS Provider

[OpenBao](https://openbao.org) is an open-source secret management system with a [Transit secrets engine](https://openbao.org/docs/secrets/transit/). Transit exposes an HTTP API; it does not itself provide the Kubernetes KMS v2 Unix gRPC service. A Gardener extension supplies the adapter and its lifecycle.

This is an illustrative provider design. Concrete field validation and the plugin belong to a separate extension. **Direct Transit wrapping** is the baseline: the plugin passes KMS `Encrypt` and `Decrypt` requests to Transit while the external Transit key remains in OpenBao. Plaintext DEK/seed material still passes through the plugin and is held by the apiserver as required by envelope encryption.

The extension registers kind `ControlPlaneEncryption` with type `openbao`, verifies key access, and injects the plugin and its authorized configuration. A provider-specific configuration could look like:

```yaml
apiVersion: openbao.provider.extensions.gardener.cloud/v1alpha1
kind: ControlPlaneEncryptionConfig
address: "https://openbao.my-company.internal:8200"
namespace: "gardener/prod"  # optional; default is root namespace
transitMount: "transit"
keyName: "shoot-encryption-key"
auth:
  method: kubernetes
  path: "auth/kubernetes-seed-eu1"
  role: "shoot-encryption"
  audience: "openbao"
caBundleResourceName: openbao-ca
```

`caBundleResourceName` denotes an authorized resource named in the Shoot's `spec.resources`, imported through Gardener's referenced-resource mechanism; it is not an arbitrary Seed Secret name. The extension must define and validate this reference contract. `address`, namespace, Transit mount, key name, and authentication settings are user input; generated state and resolved historical configuration belong in extension status and its recovery archive.

For the illustrated Kubernetes authentication, the plugin uses a projected **Seed** service account token with the configured audience. OpenBao must validate it against the Seed's issuer and TokenReview configuration, and bind the role to the intended service account and control plane namespace. The extension renews or reacquires OpenBao tokens before expiry and mounts them or keeps them in process memory. Migration to another Seed requires an authorized destination identity and, where applicable, a different auth mount. Neither login nor token validation may depend on the Shoot apiserver being unlocked first.

### Key IDs, Rotation, and Historical Decryption

The [KMS v2 protocol](https://github.com/kubernetes/kms/blob/master/apis/v2/api.proto) requires `EncryptResponse.key_id` to identify the KMS KEK, explicitly not a local KEK. The OpenBao plugin returns a stable identifier for the external Transit key and the concrete version used to wrap the DEK/seed. `Status()` reports the same key identity for the selected write version. Identifiers must satisfy the protocol's size bounds and must not contain credentials.

A versioned encoding can identify the backend, namespace, mount, key, and version through stable IDs. The provider must define unambiguous encoding and retain the mapping to historical configurations; a path alone is insufficient when endpoints, namespaces, or credentials change. KMS annotations may carry additional routing metadata but are stored in plaintext and must not expose sensitive data.

The extension discovers a newly rotated Transit key version and reports a new desired revision. The plugin continues using the pinned current version until gardenlet requests activation. During rewriting, decryption resolves each stored key ID to its original Transit key/version and retained configuration. All old versions remain enabled until the live-data transition and applicable backup retention requirements permit retirement.

Direct Transit wrapping makes remote calls for plugin cryptographic requests, not for every Kubernetes object operation: kube-apiserver caches encryption state and decryption transformers. OpenBao audit events therefore represent backend operations, not a complete per-object access audit. Latency, request volume after a cold restart, and outage behavior must be measured with realistic Shoot workloads.

## Implementation and Acceptance Criteria

Implementation extends master's existing provider API and encryption rotation flow. It must cover `provider.type: kms` and `provider.kms` validation, completed KMS revision status, CPE schema and status coordination, extension registration and readiness, webhook lifecycle, KMS checks at the existing rollout barriers, transition-scoped rewrite markers, and ShootState persistence/restoration. The existing metadata-patch and StorageVersionMigration rewrite paths, snapshot tasks, and automatic completion are reused. Required Seed and Shoot Kubernetes versions must be documented and validated. Native sidecar support is checked on the Seed; KMS v2 support is checked on the Shoot apiserver.

Production acceptance requires tests demonstrating:

- Existing local-encryption shoots retain defaulting, provider-change rotation, automatic rotation, and applicable legacy operation behavior. The documented Shoot example passes validation; partial KMS configuration, a KMS block with a local provider, and explicit `resources: [secrets]` are rejected.
- Initial KMS creation, migration from each local provider to KMS and back, and supported KMS key/configuration changes preserve data across multiple apiserver replicas with continuous concurrent writes. Local AESGCM targets retain the existing automatic-rotation requirements.
- Provider changes, external revision changes, and `rotate-etcd-encryption-key` requests complete automatically through the existing phases, without a separate completion operation. Scheduled and combined credential operations follow the documented KMS semantics. Provider status records the completed type and KMS revision only after successful activation or finalization.
- A backend rotation that changes key identity without a Shoot spec change is discovered, activates only after preparation, and causes an explicit rewrite and snapshot where backups are configured. Transparent backend rotation retaining the same identity preserves decryption without an unnecessary rewrite.
- Both existing rewrite paths work without requiring a current local key Secret for KMS. Consecutive rotations, including an explicit request under an unchanged KMS revision, cannot reuse stale reader, rewrite, migration, or snapshot completion markers.
- Interruptions at every barrier resume the same transition; partial rewrites, snapshot failures, unexpected key IDs, and concurrent configuration changes cannot prematurely retire old decryption.
- Actual stored ciphertext uses the expected provider/key after completion; control-plane progress markers alone are insufficient evidence.
- Plugin crashes, credential expiry, KMS outages, webhook unavailability, and cold apiserver restarts have the documented behavior without plaintext fallback.
- Removing KMS settings retains the CPE, namespace label, credentials, and sidecars until the last KMS reader is retired. Shoot deletion and forced deletion preserve customer key ownership and backup dependencies.
- Recovery from Seed loss and restoration of an older retained backup work using persisted historical state; any provider-generated encrypted wrapping keys survive loss of the original CPE.
- Supported Seed migration restores credentials and plugins before kube-apiserver starts; unsupported migration is rejected before source teardown. Hibernation wake-up succeeds with independent authentication bootstrap.
- Resource coverage changes rewrite added and removed resource types correctly and cannot overlap key transitions.
- One Shoot cannot select another Shoot's credentials or key configuration through provider input, status lookup, or webhook injection.

## Alternatives

### Store the KMS Plugin as a Separate Deployment in the Seed

The native Kubernetes KMS client supports Unix sockets, so it cannot directly use a ClusterIP endpoint. A standalone service would require a local socket proxy with authenticated network transport and tenant isolation. It could scale independently, but adds a network dependency on plugin calls and another component to bootstrap and recover. These calls are not made on every etcd read/write. The per-pod plugin avoids this additional service hop while still depending on its external KMS backend.

### Extend the Existing ControlPlane Extension

The existing `ControlPlane` extension manages provider control-plane components such as cloud-controller-manager. Encryption has independent rotation, retention, and teardown ordering requirements. A separate `ControlPlaneEncryption` resource avoids coupling these lifecycles and allows KMS providers independent of the Shoot's infrastructure provider.

### Manage the KMS Plugin via a DaemonSet on Seed Worker Nodes

A node-level plugin would require host sockets and explicit per-Shoot authentication and routing on shared Seed nodes. It is technically possible but introduces isolation, scheduling, and recovery complexity. Per-pod Unix sockets on `emptyDir` volumes provide a simpler isolation boundary for this proposal.

## Open Questions

1. **Main reviewer:** At least one main reviewer must be nominated before acceptance, as required by the GEP process. The metadata intentionally leaves this assignment empty rather than implying an unconfirmed reviewer.
2. **Provider implementation:** The OpenBao extension must finalize its configuration schema, immutable external key-ID encoding, and credential-reference validation. The example establishes required behavior without claiming an existing production plugin.
3. **Future cross-extension handover:** Direct changes between extension types and automatic write failover are out of scope initially. Multiple KMS stanzas currently serve transition decryption; they do not provide primary/backup write failover.
4. **Gardener-managed KMS:** A convenience provider and local wrapping-key variants may be evaluated separately. They must meet the same lifecycle and recovery guarantees and state their key custody properties explicitly.
